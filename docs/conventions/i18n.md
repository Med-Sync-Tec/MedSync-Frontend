# Internationalization and Code Language

This file covers two related but distinct things:

1. **Code language** — the language of identifiers, file names, comments, commit messages, and other developer-facing text. **Target: English. Current state: Spanish. Migration in progress.**
2. **UI language** — the language shown to end users. **Default: Spanish. Mechanism: i18n catalog (to be added).**

Keep them separate in your head. English identifiers do not mean English UI.

---

## Code language

### Rule

All code is written in English: identifiers (variables, functions, types, components, hooks), file names, folder names, route segments, comments, commit messages, branch names, ADRs, and specs.

### Current state (2026-05-12)

The existing codebase is in Spanish. Examples that need to migrate:

| Area | Example (current) | Target |
|---|---|---|
| Route segment | `/patients/:id/consultas/new` | `/patients/:id/consultations/new` |
| Folder | `features/consultations/` (already EN) | no change |
| File | `NewSOAPEntryPage.tsx` | no change |
| Identifier | `pacientes`, `nombre`, `correo` | `patients`, `name`, `email` |
| Comment | `// arma el header` | (delete unless WHY) |
| Commit | `feat: agrega vista de pacientes` | `feat: add patients view` |
| UI string | `'Iniciar sesión'` hardcoded | `t('login.submit')` with `es.json: "Iniciar sesión"` |

### Migration plan

Migrate in waves. Each wave is a separate PR per feature. Do not mix waves in the same PR — diffs become unreviewable.

| Wave | Scope | Notes |
|---|---|---|
| 1 | Folder and file renames | Use `git mv` to preserve history |
| 2 | Identifiers in non-public surfaces | Function locals, internal helpers — low blast radius |
| 3 | Public identifiers (exports, store keys, query keys) | Coordinated rename; update all call sites |
| 4 | Route URL segments | Update `<Link>` and `useNavigate` callers; communicate URL change |
| 5 | Comments and JSDoc | Translate or delete (delete if the comment is just paraphrasing the code) |
| 6 | UI strings to i18n catalog | Adds a runtime dependency — see "UI language" below |
| 7 | Commit message language | Going forward only; do not rewrite history |

### Exceptions

Stay in Spanish (do not translate):

- **Backend field names received over the wire.** Map them to English at the Zod schema boundary using `.transform()`, but the raw key from the backend stays as-is.
- **Domain terms with no clean English equivalent.** SOAP note section names (`subjetivo`, `objetivo`, `análisis`, `plan`) are clinical acronyms in both languages — SOAP itself is English. Use English (`subjective`, `objective`, `assessment`, `plan`) for fields; show the Spanish form only in the UI catalog.
- **Course/institution identifiers.** `EQ3005B`, `TEC`, etc. stay verbatim.

### Tooling to add

- **ESLint rule** to flag Spanish identifiers in new code (heuristic: dictionary lookup or a small denylist).
- **CI grep gate** that fails on a curated list of Spanish words appearing in `src/**/*.{ts,tsx}` outside i18n catalogs.
- **Codemod** for high-frequency renames (`nombre` → `name`, `correo` → `email`, `paciente` → `patient`, `consulta` → `consultation`).

## UI language

### Rule

User-facing strings live in an i18n catalog. Components reference keys, not literal strings.

```tsx
// WRONG
<button>Iniciar sesión</button>

// RIGHT
<button>{t('auth.login.submit')}</button>
```

```json
// public/locales/es.json
{
  "auth.login.submit": "Iniciar sesión"
}

// public/locales/en.json
{
  "auth.login.submit": "Log in"
}
```

### Default locale

Spanish (`es`). English (`en`) is added as the secondary locale during the migration; switching is not user-visible yet but exists for completeness.

### Library

Not yet chosen. Candidates:

- **`react-i18next`** — mature, large ecosystem, namespaces, pluralization.
- **`@lingui/react`** — better DX (extract from JSX), ICU MessageFormat.
- **Custom thin wrapper** — only if catalog stays under ~200 keys.

Open an ADR (`0008-i18n-library.md`) when this is decided.

### Conventions

- Key format: `<feature>.<area>.<purpose>`. Example: `patients.list.empty-state`, `consultations.soap.subjective`.
- Keys are kebab-case at the leaf, dot-separated for hierarchy.
- The English value is also the description — keep them human-readable.
- Date and number formatting goes through the i18n library's formatters, not inline.

### Migration of existing UI strings

1. Inventory every literal string in `src/features/**/*.tsx` and `src/components/ui/**/*.tsx`.
2. Move each to `es.json` under a key.
3. Add the English translation in `en.json`.
4. Replace the literal with `t(key)`.

Do one feature at a time. Each PR includes both the JSON entries and the component changes.

## Backend field mapping

The Quarkus backend exposes some fields in Spanish (`nombre`, `correo`). Map at the schema boundary:

```ts
const BackendUserSchema = z.object({
  nombre: z.string(),
  correo: z.string().email(),
});

export const UserSchema = BackendUserSchema.transform(({ nombre, correo }) => ({
  name: nombre,
  email: correo,
}));

export type User = z.infer<typeof UserSchema>;
```

No component or store ever sees `nombre`/`correo`. They see `name`/`email`. The mapping is the schema's job.

When the backend renames its fields to English, drop the transform — call sites are unaffected.
